# Root 高级模式测试

本分支在 System、HEV 之外提供 Root 高级模式。默认仍为 System；Root 的新入口复用现有稳定内核和业务分流规则。当前是待手机验收的测试构建。

## 手机怎么测

1. 覆盖安装测试 APK，先在 System 连接原来的节点，确认微信、网页和一个海外应用仍能使用。
2. 设置中选择 Root 高级模式，连接同一节点；KernelSU 请求授权时确认对象为 RRBOX。首次失败时导出日志，不需要反复改节点或修改 SELinux。
3. 分别打开微信 / 酷狗、TikTok / ChatGPT，再测试网页、图片或视频。日志同时看应用包名、命中规则、直连 / 代理与结束后的收发字节；单有路由记录不能证明业务请求成功。
4. 分别做一次 Wi-Fi → 流量、息屏后恢复、断开 → 重连，然后切回 System，再切 HEV，检查各模式是否仍能联网。
5. 导出完整 TXT，并告诉我失败发生在哪一步、模式 / 网络类型以及具体功能。不要一次更换多个设置，这样日志可以与操作对应。

Root 连接不调用 Android 的 VPN 建立接口，因此不会由 RRBOX 注册系统 VPN 连接。其他 VPN 的图标、Root 或网络环境检测不由这个机制保证隐藏；首次测试应先停止其他代理应用。

## 实现范围

| 环节 | 当前做法 |
|---|---|
| 网络入口 | 原生辅助进程创建独立、非持久化 TUN，经验证身份的本地套接字传递文件描述符 |
| 数据转发 | 现有 sing-box System stack 处理 TCP / UDP / IPv4 / IPv6；不增加 HEV → SOCKS 中转 |
| 应用选择 | 独立 UID 策略路由，支持全部、仅选中、选中绕过；RRBOX 自身的互联网出口绕过，防止出口循环 |
| TCP 内部回程 | 为 System stack 的两个内部对端 `172.19.0.2/32`、`fdfe:dcba:9876::2/128` 单独安装精确路由和规则，覆盖核心自身的握手回包及反向路径检查；不依赖 Android 查询 Linux main 路由表 |
| 智能分流 | 复用原国内域名 / IP、国际域名、TikTok 包名等规则；通过内核套接字诊断识别原连接 UID，失败显示未知 |
| DNS | 原始 TCP / UDP 53 请求进入核心解析，显式上游避免 Android 系统解析递归；当前物理 DNS 地址使用设备级接管规则 |
| 局域网 | 独立路由表内的私有 / 链路本地地址继续普通路由；指定 DNS 地址例外进入核心，核心对非 DNS 请求仍执行原规则 |
| IPv6 | 单独安装 IPv6 路由，不依赖物理网络先有 IPv6 默认路由；两种地址族安装失败均回滚 |
| 退出 | 心跳、启动期限、应用身份检查及独立清理守护；仅回滚本次精确规则，关闭 TUN 描述符 |

系统 DNS 可能由 netd 共享 UID 发出，不能承诺 DNS 请求逐应用归属。仅选中代理 / 选中绕过仍可能共享设备 DNS 处理；应用自己建立的加密 DNS 连接继续按普通业务规则处理。共享 UID 的多个包只能识别为一组，不能凭同一 UID 判断究竟哪个包发起请求。

Root 使用优先级 9000 及空闲独立表，启动时检查冲突；不覆盖未知现有规则，不清空系统防火墙、不依赖 nftables，也不修改全局转发开关或 SELinux。清理未获确认时显示错误并阻止继续叠加引擎，保留日志用于定位。

## 自动验证与实测边界

CI 在隔离 Linux 网络命名空间内验证真实 TUN / 文件描述符传递、UID 选路、自身绕行、IPv6、DNS 例外、实际 UDP 数据包、正常关闭、控制通道断开和辅助进程被终止后的清理；同时保留 Release 单元测试、Lint、System / HEV 真实核心及 HEV 原生 DNS 验证。

新增的 Root TCP 验证使用固定核心依赖中的真实 System stack，移除 Linux 默认的 main 表查询并模拟 Android 的终止不可达规则。测试覆盖双栈 TCP / UDP 实际收发、内部回程缺失的反例和断开后的精确清理。结果保存在 `ROOT-TCP-REPORT.json`，不以路由命令成功替代数据收发成功。

此前只有 UDP 数据包进入 TUN 的检查，未能发现 Android 环境下 TCP 内部回程缺失。首轮手机日志表现为测试会话中有 UDP 下行却没有 TCP 进入核心，切换到 System 后 TCP 恢复。本次针对该差异修复内部路径，不修改智能分流业务规则。

这些验证不覆盖手机的 KernelSU 授权策略、SELinux 域、Android netd 的全部行为及后台限制。需要上述手机操作确认；当前不把 Root 等同于更低延迟、零耗电或所有应用不可检测。

## 可选的隔离能力检查

网络实验室末尾仍保留 Root 隔离检查，可在启动失败时运行并导出 TXT。它独立创建临时、关闭、无地址的 TUN，不安装流量接管规则，不影响正在运行的 System / HEV。

## 本次检查边界

| 检查 | 能证明什么 | 不能证明什么 |
|---|---|---|
| RRBOX 启动 Root 辅助进程 | RRBOX 的授权及该进程身份 | 其他应用或终端的授权是否相同 |
| 临时 TUN 创建、保持关闭及无地址、关闭后消失 | 本次进程有能力创建和释放独立接口 | 正式流量接管、切网或崩溃恢复已通过 |
| TCP / UDP 套接字诊断 | 能否识别辅助进程自己创建的本地套接字 | 任意应用连接的 UID 均可准确获取 |
| 透明套接字选项 | 内核是否接受对应选项 | TPROXY 规则、策略路由或 UDP 转发可用 |
| `/proc/net` 计数 | 对应表本次是否可读 | 基于表扫描的应用归属可靠性 |

辅助程序仅接受固定的检查入口和 `--version`。独立超时会结束进程；TUN 不设置持久化，不配置地址、不启用接口、不添加路由或防火墙规则。正常完成时还会核实接口已消失。没有完成标记、未读完输出或超时均不能显示为通过。

临时 TUN 的生命周期依赖关闭文件描述符时释放接口的内核机制，见 [Linux TUN/TAP 文档](https://docs.kernel.org/networking/tuntap.html)。透明代理还需要额外的规则与策略路由，不能由套接字选项成功替代，见 [Linux TPROXY 文档](https://docs.kernel.org/networking/tproxy.html)。
